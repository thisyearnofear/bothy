# Measured baseline: hand-tracing a BOM versus a reviewed graph query

Date: 2026-10-04
POC: Bothy team lead
Status: **harness built and the machine side measured; the manual side is not yet
run.** Do not quote a comparison until the table below is filled in from an actual
stopwatch run.

TL;DR: `bench/gallium-bom-extract.csv` is a 6,102-row parent/child bill of
materials covering 12 platforms, 6 of which depend on primary gallium. Answering
"which 6?" by hand is the baseline. Bothy answers the same question over the
**entire** graph in ~12 ms warm. This turns the pilot metric from a promise into a
measurement.

## Why this exists

The submission asks for a next proof: *"measured time to a review-ready brief."*
A promise is worth nothing next to a number. This is the cheapest honest number
available, and it needs no buyer data, no cloud, and no outside party.

## The instrument

`bench/gallium-bom-extract.csv` — 6,102 edges, 2,385 distinct nodes, 4 columns:

```
parent_name, child_label, child_name, depth_discovered
```

Generated by a read-only breadth-first walk of the `CONTAINS` graph from 12
platforms in `supply_chain_deep`: 6 that do reach `Primary gallium`, 6 decoys that
do not. Labels observed: `System`, `Subsystem`, `Assembly`, `Subassembly`,
`Component`, `Material`, `Mineral`. All names are synthetic pack data
(MIT/Apache/CC-BY); regenerate with the notes at the end if the pack changes.

The decoys are what make it a real task. Without them the answer is "everything in
the file", and the measurement measures nothing.

## Protocol

**Task given to the tracer, verbatim:**

> Using only this spreadsheet extract, list every platform that depends on
> `Primary gallium` at any depth. A platform depends on it if following
> `parent_name → child_name` links from the platform eventually reaches a row
> whose `child_name` is `Primary gallium`. Record your answer and the time you
> started and finished.

Rules, so the number means something:

1. Spreadsheet, printout, or pencil. **No code, no scripts, no graph tooling.**
   If a formula is used, say which, because VLOOKUP chains are part of what is
   being measured, not cheating.
2. Stopwatch starts when the file is opened, stops when the answer list is
   written down. Note any break.
3. Record the answer, not just the time — accuracy is the more interesting half.
4. One attempt per person. A second attempt measures learning, not the baseline.
5. Do not show the tracer this document; the answer key is in it.

## Results — Bothy side (measured 4 October, venue stack)

`POST /api/graph/scenario/gallium-exposure/run` against the local agent on `:8787`,
four consecutive runs:

| Run | Wall clock | Rows |
|---|---|---|
| 1 (cold) | 177.8 ms | 34 |
| 2 | 21.0 ms | 34 |
| 3 | 11.8 ms | 34 |
| 4 | 12.8 ms | 34 |

Warm ≈ **12 ms**, and that is end-to-end HTTP through the agent, the sidecar, the
graph, and the capture write — not a database-internal timer. The response carries
its own provenance envelope: `graphCommit`, `queryHash`, `capturedAt`, `runId`,
`sourceBoundary`, `ms`, `evidence`.

The chain-explanation scenario (`gallium-chain`, 10 sampled rows across 8 stages)
measured 151.9 ms cold, 16.8–17.5 ms warm.

Scope note, and it favours Bothy: **12 ms answers the question for all 133k nodes
and returns 34 platforms. The manual task is bounded to 12 platforms.** These are
not the same question, and the comparison must be stated that way.

## Time to a review-ready brief (second metric, still open)

The headline pilot metric is not query latency, it is *time to a review-ready
brief* — query, draft, citation inspection, reviewer sign-off. That path needs a
verified reviewer identity, so it cannot be measured on the unconfigured local
agent (approval is disabled by design; see
`docs/proof-no-self-approval.md`).

To measure it: bring up the disposable-SSO stack per
`docs/demo-sso-rehearsal.md`, then time the walkthrough from "sign in as analyst"
to "reviewer has approved the cited brief". Report it as a separate number from
the query time. Do not add them together and call it the comparison.

## What this measurement does not establish

- **n = 1, and the tracer is probably the builder.** A builder tracing their own
  synthetic data is not a defence-prime analyst. Label it accordingly or the number
  is worthless.
- **6,102 rows is small.** A real prime's BOM is orders of magnitude larger and
  split across ERP, PLM and supplier portals. This is a lower bound on manual cost,
  not an estimate of it. Say "understates", never "represents".
- **The extract is a single clean table.** Real inputs are several tables with
  inconsistent part naming, which is the actual reason exposure goes unnoticed.
  This measurement does not capture that, and it is the strongest argument that the
  number is conservative.
- **The graph answer is limited and sampled.** 34 platform names, query limit 50,
  from synthetic data. It is not a total exposure count and it establishes no
  programme stoppage.
- **Speed is not the pilot success criterion.** A 12 ms query nobody trusts is
  worse than a slow answer someone can defend. The claim being tested is
  *defensible*, and fast is a side effect.

## Reproducing the instrument

The generator was a throwaway read-only script (BFS over `CONTAINS`, 8 levels, 12
seeds). To regenerate after a pack change, walk `supply_chain_deep` from 6
gallium-reaching platforms plus 6 that do not, emit
`parent_name, child_label, child_name, depth_discovered`, and update the answer key
above. Every query is a read; never run it against a graph you intend to keep
clean, and re-check the decoy set actually excludes gallium before trusting the
comparison.
